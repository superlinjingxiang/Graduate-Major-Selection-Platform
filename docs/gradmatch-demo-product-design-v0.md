# GradMatch 产品设计与 Demo 需求（V0.1）

> 状态：讨论稿，可持续修改  
> 更新日期：2026-09-09  
> 当前阶段：Web 优先的高保真 Demo  
> 文档目的：集中记录已经确认的产品方向、页面体验、商业边界与 Demo 验收要求。本文不替代正式 PRD、数据审核规范或生产发布门槛。

## 1. 产品定位与经营目标

GradMatch 面向准备研究生考试的用户，帮助其理解全国考研趋势、查找院校和专业、比较招生项目，并形成可解释、可核验的择校决策。

产品的核心经营目标是形成可持续利润，但盈利必须建立在真实用户价值和可信数据之上。平台不能通过制造焦虑、隐藏影响决策的关键事实、出售用户线索或用商业合作干预自然结果获利。

一句话定位：

> 用可信数据和可解释工具，帮助考研用户减少信息差，更高效地完成院校与专业选择。

## 2. 产品范围

### 2.1 长期产品方向

- 面向全国研究生考试用户提供宏观数据、院校和专业基础信息。
- 所有研究生专业逐步建设基础档案，并提供一致的基础选择功能，不把计算机或其他单一专业设为产品主线。
- 基础选择功能至少包含专业名称与代码、学位类型、招生单位、培养单位、地区、学习方式、考试科目、招生年度、公开计划口径、来源与数据状态。
- 招生变化、项目对比和个性化匹配采用通用能力建设；后续可以根据用户需求与数据条件增加某些专业的深度字段，但不能影响其他专业的基础可用性。
- 第一阶段只建设 Web 平台；未来使用 Expo/React Native 同时扩展 Android 和 iOS。
- 业务规则、接口客户端、设计令牌和数据模型必须保持平台无关，支持移动端复用。

### 2.2 真实数据覆盖策略

正式产品目标是覆盖全国所有研究生专业的基础选择功能。真实数据仍需分批接入和审核：每批公开其覆盖院校、专业、年度和字段完整度，未完成来源核验的内容不得因 Demo 展示而被宣称为全国完整覆盖。现有正式文档中的“2027 北京计算机相关专业试点”属于旧范围，后续同步正式 PRD 时应予以修订。

### 2.3 Demo 展示范围

Demo 用于验证产品价值、信息架构和视觉质量，可以展示全国宏观总览和少量代表性院校/专业样本，但必须区分：

- 官方历史数据；
- 尚未发布的年度字段；
- 演示用样本数据；
- 已核验与待核验内容。

Demo 不等于生产上线，不接真实支付，不承诺全国数据已完整，不展示虚构的录取概率。

## 3. 核心用户与主要任务

主要用户是正在准备考研、需要确定院校和专业的学生。未来可服务家长、老师和咨询人员，但考生本人始终拥有个人数据与最终决策权。

核心任务：

1. 了解今年和往年的考研整体趋势。
2. 通过学校名称、专业名称或专业代码快速找到目标。
3. 了解具体院校和专业的招生事实、变化及来源。
4. 在统一口径下比较多个项目。
5. 保存候选、接收变化提醒并形成个人方案。
6. 理解结论依据、不确定性和下一步需要核验的事项。

## 4. 产品与体验原则

- **先有价值，再要求登录**：游客可以搜索、查看基础数据和进行临时比较。
- **官方来源优先**：重要结论必须能回到原始来源。
- **未知就是未知**：没有可靠数据时显示“暂无官方数据”或“待发布”，不能猜测。
- **不预测录取概率**：平台提供条件匹配和决策辅助，不承诺考试或录取结果。
- **公开页面不暴露内部运行信息**：服务状态、环境、版本和依赖连接情况只供内部运维使用。
- **清晰胜过堆叠**：页面围绕用户任务组织，不展示与用户无关的技术说明。
- **移动优先兼容**：Web 页面从第一版开始支持桌面、平板和手机。
- **商业结果不影响自然结果**：广告和合作内容必须明确标识并与自然搜索、推荐隔离。

## 5. 整体信息架构

顶部导航保持简洁、稳定：

- 首页
- 数据
- 院校
- 专业
- 择校工具
- 资讯
- 登录/个人账户

主要公开页面：

1. 数据型首页；
2. 搜索与筛选结果页；
3. 院校详情页；
4. 专业/招生项目详情页；
5. 项目对比页；
6. 择校工具与个人报告页；
7. 招生变化与资讯页；
8. 登录、注册和账户设置页。

## 6. 首页设计

首页采用“数据叙事型”视觉方向，参考苹果官网的信息层级、聚焦能力和留白节奏，但不复制其具体样式。

### 6.1 页面结构

1. **首屏价值主张与统一搜索**  
   使用一句清晰的价值表达和一个主要搜索框。搜索框同时接受学校名称、专业名称和专业代码。首屏不展示平台运行状态、开发环境或技术栈。

2. **全国考研数据总览**  
   展示今年与往年报名人数趋势、招生相关宏观数据、学硕与专硕结构等用户真正关心的信息。每项数据紧邻年份、统计口径、来源和更新时间。

3. **专业分类与热门方向区域**  
   按学科门类、专业学位类别和热门方向提供入口，并展示适用于不同专业的招生变化、考试科目和项目对比能力。

4. **免费择校工具**  
   提供院校搜索、专业查询、临时对比、基础筛选等无需登录即可体验的能力。

5. **最新招生变化**  
   展示有明确来源的停招、改考、专业目录、学费或招生计划变化，不用普通资讯填充页面。

6. **会员能力预览**  
   在用户理解免费价值后，展示高级对比、持续提醒和个性化报告，不使用强制弹窗。

7. **页脚与信任入口**  
   包含数据来源说明、纠错入口、免责声明、隐私政策和用户协议。

### 6.2 首页数据边界

- 报名人数、招生人数和录取人数必须明确区分。
- 计划数、推免计划、统考计划和实际录取不能混用。
- 学硕/专硕占比必须说明统计对象、年度和数据来源。
- 2027 正式数据尚未发布时，不得以 2026 数据冒充。
- 可用于 Demo 的已知官方数据包括：2026 年全国硕士研究生招生考试报名人数 343 万、2025 年 388 万；页面实现时仍需再次核验链接和口径。

参考来源：

- [教育部：2026 年全国硕士研究生招生考试报名人数](https://www.moe.gov.cn/jyb_xwfb/gzdt_gzdt/moe_1485/202511/t20251124_1421370.html)
- [教育部：2025 年全国硕士研究生招生考试报名人数](https://www.moe.gov.cn/jyb_xwfb/gzdt_gzdt/moe_1485/202411/t20241121_1163982.html)

## 7. 搜索、结果与详情页

### 7.1 统一搜索

- 一个搜索框支持学校名称、专业名称和专业代码。
- 输入时按“院校、专业、专业代码”分组提供建议。
- 支持地区、院校属性、学硕/专硕、全日制/非全日制等筛选。
- 无结果时提供近似匹配、检查建议和纠错入口。

### 7.2 结果分层

- 全国院校和专业展示基础档案。
- 所有专业使用一致的基础字段和状态规则；存在更多已核验数据的专业可以展示扩展字段，但搜索排序不得因此把它们伪装成更适合用户。
- 每个重要字段显示“已确认、待发布、来源冲突、可能过期”等状态。
- 游客可以建立临时对比；保存、跨设备同步、持续提醒和个人报告需要登录。

### 7.3 公开详情页

- 院校页、专业页和年度招生项目页使用稳定地址，并支持搜索引擎收录。
- 详情页优先展示用户做决定需要的事实，不堆砌学校宣传内容。
- 每项时效性事实提供来源、适用年度、发布时间或采集时间。

## 8. 登录与统一账户

### 8.1 登录方式

- 主要方式：微信扫码登录、手机号验证码登录。
- 其他方式：QQ 登录、邮箱验证码、邮箱密码。
- iOS 应用上线时再评估 Sign in with Apple。
- 未获得官方开放权限前，不接入学信网账号登录。
- 密码要求采用合理强度，不以过长的最低位数制造不必要门槛；输入框提供显示/隐藏密码按钮。

### 8.2 账户规则

- 微信、QQ、手机号和邮箱是同一账户下可绑定的身份，不建立互相孤立的账户体系。
- 只有完成身份验证后才允许合并账户；不能静默合并可能属于不同用户的身份。
- 绑定和解绑需要重新验证，并确保账户至少保留一种可用登录方式。
- 游客登录后提示迁移本地收藏和临时对比，不直接覆盖已有云端数据。
- 登录成功后返回登录前页面，继续刚才的搜索、比较或保存操作。

## 9. 访问权限与盈利模式

### 9.1 权限边界

- **游客**：查看全国基础数据、搜索院校专业、查看公开详情、进行有限临时对比。
- **免费注册用户**：保存少量院校、建立基础档案、跨设备同步和接收必要提醒。
- **会员用户**：更多对比、历年趋势、高级筛选、招生变化监控和完整收藏管理。
- **深度报告用户**：购买一次性个性化择校报告，或使用会员包含的报告额度。

影响资格或结论的关键事实、官方来源以及严重错误更正提醒不得放在付费墙之后。

### 9.2 商业规则

- 个性化报告展示推荐理由、匹配因素、证据和不确定性，不展示缺乏可靠模型依据的精确录取概率。
- 第一阶段不依赖广告盈利。
- 未来推广内容必须明确标记“推广”，不能混入自然结果。
- 支付预留微信支付和支付宝。
- 订单、会员权益、报告额度、退款和发票分别建模，不能只在用户表增加一个会员字段。
- 真实支付在经营主体、订单协议、退款、对账、开票和消费者权益流程准备完成后才能开放。

## 10. 数据可信度与更新机制

### 10.1 来源等级

1. 教育部、研招网、院校研究生院、官方招生简章和招生目录是主要依据。
2. 院系与其他官方页面可补充信息，但不能覆盖更高等级的正式招生文件。
3. 第三方平台、媒体和用户投稿只能用于发现线索或辅助解释，不能作为关键事实的唯一依据。

### 10.2 字段与版本

每项可变数据至少保存：

- 数值或文本值；
- 单位与统计口径；
- 适用范围与招生年度；
- 来源地址或原始文件；
- 来源发布日期和采集时间；
- 数据状态与审核记录。

数据按年份和版本保存。发布新数据时不覆盖历史记录，确保旧报告和往年趋势仍可复核。

### 10.3 更新流程

数据处理链路：

> 获取并保存原始网页/文件 → 解析候选事实 → 结构与跨年合理性校验 → 冲突检查 → 必要的人工审核 → 发布不可变版本 → 清理缓存 → 重算受影响内容 → 发送提醒

- 抓取失败时保留最近一次已确认数据，并标记可能过期。
- 多个官方来源冲突时展示不同口径，暂停确定性结论。
- 用户纠错生成审核工单，不能直接修改公开数据。
- 纠错通过后新增版本，并幂等重算对比、快照、提醒和报告。
- 测试 fixture 与真实数据完全隔离，不得进入正式页面。

## 11. 技术架构

采用 Web 优先、面向移动端复用的 Monorepo 和模块化单体：

- `apps/web`：Next.js App Router、React、TypeScript strict。
- `services/api`：Django 5.2 LTS、Django Ninja、Django Admin。
- PostgreSQL：结构化业务数据与版本记录。
- Redis：缓存、限流和 Celery 队列。
- S3 兼容对象存储：原始网页、招生文件、快照和报告文件。
- Celery：采集、解析、变更检测、提醒和报告生成。
- `packages/api-client`：从 OpenAPI 生成接口客户端，不重复手写 DTO。
- `packages/domain`：平台无关业务规则、Zod 模型和查询定义。
- `packages/design-tokens`：Web 与未来移动端共享的颜色、字体、间距、圆角、阴影和动效参数。

后端按账户、院校专业、招生数据、来源审核、搜索对比、用户档案、提醒报告、会员订单划分模块。Web 和未来移动端只通过 API 使用业务数据，不直接连接数据库。

第一阶段使用 PostgreSQL 索引与模糊匹配完成搜索，不引入微服务、Kubernetes、GraphQL 或独立搜索引擎。

## 12. 前端视觉与性能

- 使用大标题、大数字、克制色彩、充足留白和全宽内容区形成成熟的数据产品感。
- 使用统一设计令牌，避免登录页、首页和工具页面风格割裂。
- Web 组件采用 Tailwind、Radix 和可修改的 shadcn 源码；未来移动端使用 NativeWind、原生组件和 Reanimated。
- 首页和公开详情页优先使用 Server Components，减少浏览器端 JavaScript。
- 搜索建议、筛选和对比等交互区域才使用 Client Components。
- 图表和重型模块按需加载；图片使用响应式尺寸、现代格式和懒加载。
- 动效用于解释数据和提供操作反馈，支持系统“减少动态效果”设置。
- 页面必须适配手机、平板和桌面，并保证键盘操作、清晰焦点和非颜色状态提示。

## 13. 安全、隐私与异常处理

- 密码只保存安全哈希，日志、后台和分析系统不能记录明文密码或验证码。
- Web 使用 Secure、HttpOnly、SameSite Cookie；未来移动端使用受保护的会话令牌，不自行引入 JWT。
- 注册、登录、验证码、找回密码和敏感接口统一限流，并防止账户枚举。
- 用户成绩、偏好和目标院校默认仅本人可见。
- 用户档案遵循最少采集原则，不要求身份证件、精确地址或完整成绩单。
- API 使用统一错误结构，区分参数错误、未登录、无权限、限流、数据缺失和系统异常。
- 页面只显示用户可理解的恢复建议，不展示数据库、缓存、对象存储、堆栈或内部服务诊断。
- 支付回调必须验签并支持幂等处理。
- 数据发布、账户合并、会员调整和退款等关键操作保留审计日志。
- 提供隐私政策、用户协议、纠错、账户注销和个人数据删除入口。

## 14. 高保真 Demo 范围

Demo 推荐围绕一条完整用户链路制作，而不是制作大量彼此孤立的静态页面：

> 首页看到有价值的数据 → 搜索任意专业或院校 → 查看结果与数据来源 → 加入两个项目进行对比 → 尝试保存 → 出现登录入口 → 登录后保存成功

### 14.1 Demo 必做页面

1. **数据型首页**：包含统一搜索、全国趋势、学硕/专硕结构、专业分类入口、免费工具和最新变化。
2. **搜索结果页**：支持院校/专业/代码搜索建议、筛选，并以一致结构呈现不同专业的基础信息。
3. **项目详情页**：展示年度、考试科目、计划口径、费用、状态、来源和更新时间。
4. **项目对比页**：并排比较两个或三个项目，突出差异、缺失值和来源状态。
5. **登录界面**：微信扫码和手机号验证码为主要入口，QQ、邮箱验证码和邮箱密码为其他方式。

### 14.2 Demo 数据策略

- 宏观数字使用可核验的官方历史数据。
- 院校和专业采用少量代表性样本，不追求全国完整数量。
- 尚未核验的数据明确标记为演示数据或待确认，不伪装成正式事实。
- Demo 可以使用前端 mock 或本地种子数据；真实采集、支付和第三方授权登录不属于本轮必做范围。

### 14.3 Demo 暂不实现

- 真实微信、QQ、短信和支付渠道；
- 全国院校与专业的完整数据采集；
- 真实个性化推荐模型和录取概率；
- 生产级会员结算、退款和发票；
- Expo 移动应用；
- 面向公开生产环境的完整合规发布。

## 15. Demo 验收标准

1. 首屏能在数秒内让用户理解平台用途，并直接开始搜索。
2. 首页不再出现开发说明、系统运行状态或技术栈介绍。
3. 首页至少展示一组有来源、年份和口径的全国趋势数据。
4. 搜索框能识别至少一所院校、一个专业名称和一个专业代码。
5. 用户可以从搜索结果进入详情，并把两个项目加入临时对比。
6. 每项关键数据都能看到状态、年度和来源入口；未知值不伪造。
7. 游客可完成浏览与临时对比，保存操作自然触发登录。
8. 登录界面完整展示已确认的登录方式与账户结构，但 Demo 不发送真实短信或调用真实第三方授权。
9. 桌面端达到高保真视觉质量，手机端不存在横向溢出或无法操作的关键功能。
10. 页面交互流畅，无明显布局跳动；动效关闭后仍能正常使用。
11. Demo 数据、正式数据和测试 fixture 有清晰边界。
12. 所有公开错误信息均面向用户，不暴露内部服务状态。

## 16. Demo 测试重点

- 首页、搜索、详情、对比和登录主链路端到端测试。
- 搜索无结果、近似结果、加载失败和重试状态。
- 数据待发布、过期和来源冲突的展示。
- 游客临时数据在模拟登录后的迁移与不覆盖规则。
- 密码显示/隐藏、表单键盘操作与错误提示。
- 桌面与手机视口的布局测试。
- Server Components 与客户端交互边界、Web 构建和 TypeScript strict 检查。
- 无真实外部站点、短信、OAuth 或支付请求的测试约束。
