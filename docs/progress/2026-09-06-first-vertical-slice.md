# GradMatch 首个纵向链路进度记录 — 更新至 2026-09-07

## 当前结论

GradMatch V1.3 首个纵向链路的代码与隔离自动化验收已完成。工程链路使用冻结清单中的 3 个代表项目，邀请制前的 `CoverageManifest` 仍固定为 10 个项目，二者口径没有混用。

这不是公开发布或盈利可行性结论。真实 2027 官方证据尚未发布时，三个工程项目只能返回 `needs_confirmation`，决策快照为 `awaiting_official_information`。AI、支付、移动端页面和真实网站采集继续关闭。

## 已完成链路

1. 冻结 2027 年、北京、全日制、全国统考、计算机相关试点范围和目录分母。
2. 保存来源访问记录与不可变原始数据块，建立证据主张、审核、发布和规则版本。
3. 创建访客确认事实，并对三个代表项目生成资格三态结果。
4. 确定性生成比较运行、分组、顺序、结果哈希和访客决策快照。
5. 使用资源范围能力凭证访问访客数据；只有已验证主邮箱账户与有效凭证同时存在时才能认领。
6. 提交纠错，由具有明确角色的工作人员独立审核和发布；Celery beat 自动扫描事务出箱，投递失败可在租约到期后恢复。
7. 同一出箱事件处理两次只创建一个有效作业和一个新结果版本；每个受影响快照各产生一条幂等更新，连续纠错仍能从原快照看到差异，旧结果与旧快照不覆盖。
8. 同一测试数据库内放入 `synthetic`、`test_fixture`、`reference_year=2026` 数据，并验证它们不进入公开响应或真实结论。
9. Web 提供试点范围、项目、事实确认、比较结果、快照和纠错交互；公开页面不展示运行状态或内部诊断。
10. Windows 原生诊断和启动器读取同一 `.env`，Docker Compose 保留为可选部署方式。

## 评审修复

Task 9 评审修复了待定证据可能显示确定结论、CSRF 重试复用已消费请求，以及 Next 错误边界接口不正确的问题。

Task 10 评审修复了：

- 同一 manifest 内跨项目规则串用，以及另一 manifest 规则误入当前试点；
- 未验证邮箱账户可以认领访客快照；
- 原生诊断可能通过 `uv run` 隐式创建环境或访问网络；
- `.env` 只被诊断读取、应用进程却未使用同一配置；
- 原生代理路径文档超过 Next.js 实际 rewrites；
- 仅替换高级 socket helper、无法完整阻断测试网络访问。

最终 Task 10 独立复核确认上述问题全部关闭。随后进行的全分支复核又发现事务出箱未自动投递、同一规则族并发纠错可能从旧修订克隆、快照更新不完整、内部诊断接口未鉴权、事实值缺少类型约束，以及审核职责和管理后台可绕过的问题。本轮已逐项补上：

- 增加每分钟运行的出箱投递任务、`skip_locked` 批量租约、失败后的超时重试，以及发布到处理器的 E2E；
- 使用稳定的年度招生项目行锁串行化同一项目的规则族修订，锁后重读最新修订，并增加顺序回归测试和可在 PostgreSQL 下启用的并发测试；
- 对同一比较运行的全部历史快照生成逐事件幂等更新，覆盖多快照和连续纠错；
- 将就绪状态和构建元数据限制为工作人员接口，仅保留公开粗粒度存活检查；
- 将用户事实改为严格布尔值、整数、试点枚举和规范化文本，非法值返回 422；
- 记录来源、证据声明和规则集的创建者，使用 `editor`、`reviewer`、`administrator` 角色约束审核与发布，并把工作流历史后台改为只读。

2026-09-07 的后续全分支复核又发现五个边界问题，本轮继续关闭：

- 纠错事件在发布时保存三个工程项目的精确规则版本，并记录全局前驱事件；即使两个连续纠错都已发布、任务又乱序到达，也会依次生成中间结果和最终结果，不会跳过或回退版本；
- 新规则修订号从同一规则族的所有状态中取最大值后递增，已有未发布草稿时不再发生唯一键冲突；
- 证据声明、规则集和纠错替换来源的创建者必须具有 `editor` 角色，纠错新增“审核中”状态、指派审核人和审核开始时间，只有该审核人可以接受或拒绝；
- 每个受影响快照生成一条幂等站内通知；快照接口和结果页展示纠正字段、旧值、新值、官方来源、结果差异和下一步行动，但不暴露内部出箱、存储键或审核备注；
- 目标年份使用严格整数约束，`2027.0`、字符串和试点外年份均返回 422。
